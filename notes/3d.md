# Spaces and the 3D arm

## Spaces

A bundle declares manifolds; every field and point set names its `domain`
(or falls back to `defaultManifold`, which is only required when something
omits `domain`). The viewer lists the bundle's 2D and 3D manifolds that carry
at least one buildable field in the bundle panel's **space** picker
(`?space=id`); the selected space decides which arm renders:

* 2D → the panels `2D space`, `colorfield`, `isolines`, `streamlines`, `vector
  field` and the Canvas 2D / WebGPU renderers of `main.ts`;
* 3D → `3D space`, `colorfield` (planes through the volume, see below),
  `isosurfaces` and `view3d.ts` (WebGPU only).

The `space` and `isolines` panels are one set of DOM controls shared by both
arms: their titles switch (`isolines` ↔ `isosurfaces`), rows and buttons that
exist in one arm only carry `.d2` / `.d3` (hidden by `body.dim3` /
`body:not(.dim3)`). So `value`, `split`, `opacity` and the ▶ animation mean
the same thing in both: levels of the I_V field, evenly split around `value`
in the field's codomain.

Fields, point sets, slot selections (`sel`), the view / camera and the
animation directions belong to a space; options are stored per bundle with a
per-space section (`tensatory.opts.<file>` → `spaces[id]`). The mappings
matrix only shows the columns a space has (`SlotDef.present`); every column
is present in both arms now (C got its 3D meaning with the colorfield planes).

The symbolic example bundles are `symbolic2d.json` (four planes: bowl +
saddle, Rosenbrock, Gaussian mixture with A/B/C, waves) and `symbolic3d.json`
(four volumes: spheres and tori, Gaussian mixture with A/B/C, gyroid,
Rosenbrock). Space names carry no dimension suffix: the bundle already says
which it is.

## Isosurfaces: marching tetrahedra

`core/src/iso/marchingTets.ts`. Every grid cell is split into the six
tetrahedra around its (0,0,0)–(1,1,1) diagonal; each tet yields 0–2 triangles
whose vertices are linear zero crossings of f − level on its edges. Tables
(`CUBE`, `TETS`, `TET_EDGES`, `TET_TRIANGLES`) are computed once at load and
shared with the GPU kernel, so both sides emit identical triangles.

Output is a **triangle soup** (`IsoMesh`: positions, normals, optional
values, 3 vertices per triangle) — no welding, so it maps 1:1 to a GPU kernel
appending through an atomic counter. Normals are the field gradient — the
exact symbolic gradient at the vertex, or central differences of the grid
values interpolated along the edge — pointing towards **increasing** field
values; triangles are wound counter-clockwise from that side, so shading and
geometric normals agree. Colour is evaluated at the vertex (`colourAt`, used
for I_C on both backends) or interpolated from a second grid (`colour`).

`packages/gpu/src/mesh.ts`: `Vert { p: vec3, c: f32, n: vec3, pad }` (32
bytes), `MeshIndirect { vertexCount: atomic, 1, 0, 0 }` for `drawIndirect`,
`allocMesh / resetMesh / packMesh / uploadMesh / readMesh`, and
`fusedIsosurface(backend, values, gradient?, colour?)` — one thread per cell,
the shared tables as WGSL `const` arrays, normals from the gradient program
or from the resident values, colour from the colour program. Tests compare
the two backends as sorted vertex multisets (positions, normals, values to
4 digits) on a symbolic ball with exact normals and colour, and on a sampled
gyroid with NaN holes and difference normals.

### Exact surfaces (analytic gradients)

As in 2D, the grid only seeds topology for symbolic fields: every vertex is
projected onto the true level set along the exact ∇f (`projectToLevel` on the
CPU — it was already dimension-generic — and `projection3Wgsl` on the GPU:
damped Newton, bisection fallback, box faces locked), and the normal is ∇f at
the projected point. Shared edge vertices project identically, so the soup
stays watertight. Flag ∇ (`isoExact`) in the isosurfaces panel; sampled and
blurred fields keep their linear vertices. Tests: the projected unit sphere
agrees between backends to 2e-5 (f32 Newton).

### Blur

`metric` (box blur, N-D on both backends: `boxBlur`, `blurResidentSync`)
applies to the volume before contouring; a blurred field is contoured
linearly with difference normals.

### Surface smoothing

`smoothMesh.ts`: the soup is welded by exact position (a shared edge's vertex
is computed identically in every tetrahedron, so no edge keys are needed),
smoothed with Taubin λ = 0.5 / μ = −0.53 passes, given area-weighted face
normals (optionally averaged), and expanded back. The `line` control reads
`surface` in 3D and applies to non-exact meshes (exact surfaces are already
on the level set); it runs on the CPU, so `compute = gpu` falls back to CPU
meshing while it is set — a fused version needs welded connectivity on the
device (an edge-indexed vertex buffer like `smoothedIsolines` in 2D).

## Crop and face outlines

Ported from the prototype: the `x / y / z` rows of the `3D space` panel are
interval sliders (`interval.ts`, plain variant): an empty bar shows the whole
box, a half interval crops one side, a full interval keeps a slab (fractions
of the box; `?cropx=lo,hi`, `null` = open end). Every gesture (drag, wheel,
shift-hover) updates the picture live: the meshes are not touched by a crop
(fragments outside the planes are discarded, `cropMin` / `cropMax`), and the
face outlines are built so that a crop change is only re-dispatches — see
below. (A first version compiled new sampling programs and marching-squares
kernels per face position, ~0.5 s per change; the dotted-preview code path in
`main.ts` / `View3D.overlay` remains available should a gesture become
expensive again.) The box outline follows the crop, and the **isolines of I_V
on the six faces of the cropped box** show where each isosurface meets them — the intersection is far
easier to read from these outlines than from the shells alone (`outline`
flag). Each face is a 2D grid with the volume grid's spacing; its values are

* the field sampled exactly on the plane (exact symbolic case), contoured with
  the exact 2D machinery — `sliceScalarField` restricts a field to a plane
  with exact derivatives for `contourField`; the fused 2D isoline kernel takes
  a `slice` of the 3D field (3D programs wrapped as 2D functions on the plane);
* otherwise the (blurred / sampled) volume grid itself, trilinearly sampled
  on the plane (`sliceResidentSync`, `DenseScalarFieldData.sampleOn`), so the
  outlines coincide with the mesh boundary by construction.

They are drawn as 2D `Seg` records embedded on the face plane by the 3D line
pipeline. Every face (axis, side) owns one 2D grid — the cropped box's face
at the volume grid's spacing — one values buffer, one plane pass
(`planeSampler` for the exact field, `planeSlicer` for the volume grid; the
depth is a per-dispatch parameter) and one 2D kernel (`fusedIsolines` with a
`slice` whose depth also comes from the params buffer) plus a segment set per
level, all built once per (field, grid).

**The volume grid follows the cropped box**: the adaptive resolution is spent
inside the crop, so cropping a small cube is a close-up at full resolution
instead of a slice of the coarse full-box grid. A crop change therefore means
new grids (values, meshes, faces); crop drags run in the `moving` tier like a
2D pan and the fine grid returns when the drag settles
([resolution.md](resolution.md)). The renderer's crop planes still trim
anything that pokes out (projected vertices).

## The colorfield: planes through the volume

The `colorfield` panel is shared with the 2D arm (its tick, the `c` key, the
`smooth` flag and the C column of the fields matrix mean the same); in 3D it
gains three rows `x` / `y` / `z`, one NULLABLE slider each, and the C field
is computed on every plane `axis = value` whose slider is set and embedded in
the picture as a flat colormapped quad. The panel is OFF by default in 3D
(`showScalar` is saved per arm like the streamline controls: `ui` in 2D, `ui3`
in 3D, 3D default off — a 3D space's first visit still turns the isosurfaces
on). All three sliders start SET: each spans the C field's box along its axis
(`setRange`, continuous), and its initial coordinate is the space's `origin`
on that axis when the manifold declares one that lies inside the box, else
the box's centre (`planeDefault`). Clicking a handle (or Backspace) drops that
plane, clicking an empty bar adds it back where clicked. State:
`state.planes[axis]` = coordinate | null (dropped) | undefined (default not
resolved yet); `syncPlaneRows` (every 3D frame) re-fits the sliders when the C
field or its box changes (a box zoom, another field) and resolves a
coordinate that is unset or fell outside the new box to the default — a
dropped plane stays dropped. Saved per space (`planes: { axis: value | null
}`), carried into a sweep member's same space. Under them an `opacity` row
(`planeAlpha`, a nullable slider that starts UNSET = opaque; an ordinary
per-bundle `ui` value) applies to all the planes.

Rendering: `GpuPlaneLayer3D` in `GpuScene3D.planes` (`render3d.ts` `PLANE3`):
a quad over the field's box ∩ the cropped box on the plane. Opaque planes
are drawn in the OPAQUE pass with depth write, so shells behind them hide and
translucent shells in front composite over them through the OIT pass; with
`alpha` < 1 (`fsTrans`, the `planesTrans` pipeline) a plane joins the
weighted-blended OIT pass itself, depth-tested against the opaque image
without writing, like translucent shells and lines. The fragment reads a
resident 2D grid exactly as the 2D raster does (bilinear / nearest, the LUT,
alpha < ½ = masked by the colormap interval selection, NaN = outside the field
→ discard), unlit so the colours match the legend; the crop planes trim it
like everything else (a plane outside the crop slab is simply not there). The
plane's grid axes are the two kept axes in ascending order, as `embed` lifts
the face outlines.

Sampling (`View3D.planeLayer`): GPU compute reuses the face outlines' PLANE
PASSES — `planeSampler` evaluates the field exactly on the plane's 2D grid; a
costly (net) field goes through `colourSource`, i.e. its capped resident
volume grid (64³) sliced trilinearly by `planeSlicer`, as its colours on
vertices do — built once per (field, axis, grid) and RE-DISPATCHED per depth
into one values buffer, so dragging a slider is a single small dispatch per
frame. CPU compute samples a degenerate 3D grid (size 1 along the axis) and
uploads per depth. The plane grid has `PLANE_SCALE` (4) × the volume
resolution along its longest side, capped at `PLANE_MAX` (1024) — a plane is
n² work, not n³ — and 64 for a costly field on the CPU. The planes take
part in `redo()` (a remeasure re-dispatches them) and the memory cap.

## Rendering: `GpuRenderer3D`

Orbit camera (`target`, `distance`, `fov` and `rot`, a unit quaternion taking
the camera frame — x right, y up, z towards the eye — to world; `quatMul` /
`quatAxisAngle` / `quatRotate` / `quatLook` / `cameraAxes` in `render3d.ts`),
column-major matrices (`perspective`, `mul4`, `project`; the view matrix is
the inverse rigid transform of the camera's axes). The camera used to be
yaw / pitch with the pitch clamped to ±1.5: a fling towards a pole ran into
the clamp and stuck there (gimbal lock). Saved yaw / pitch cameras are
converted on load (`savedCamera` in main.ts). The
mesh pipeline pulls `Vert` records from the storage buffer by vertex index
(no vertex buffers), shades two-sided with a headlight (normal flipped to
face the eye, the far side 20 % darker so nested shells read inside/outside),
and colours by the vertex value through the same `param` codomain mapping and
256-entry LUT texture as the 2D renderer (masked LUT alpha → discard).

Translucency is **weighted-blended OIT** (McGuire & Bavoil): layers with
α ≥ 0.999 are drawn first into the colour + depth buffers; translucent layers
are drawn depth-tested (no write) into an `rgba16float` accumulation target
(`Σ w·α·rgb`, `Σ w·α`) and an `r16float` revealage target (`Π (1 − α)`, blend
`zero / one-minus-src`), then a full-screen pass composites
`accum.rgb / accum.a` with alpha `1 − reveal` over the opaque image. No
sorting, no peeling; the depth weight `w(z, α)` is the paper's simple form.

**Lines** (`lines3d.ts`, `Seg3 { a, ca, b, cb, arc, len, phase }`, 48 bytes):
a thick-line pipeline draws screen-space quads (width in css px, perpendicular
to the projected segment), depth-tested and written in the opaque pass, LUT or
solid colour, particle windows as in 2D, crop discard. Records are read as raw
floats so the same pipeline draws Seg3 sets and 2D `Seg` sets embedded on a
box face (`embed: {axis, depth}`). The box outline, ordered point sets and the
face outlines use it; points and labels stay on the Canvas 2D overlay (`#gl`)
projected with the frame's view-projection (not depth-tested).

## The viewer arm: `view3d.ts`

`View3D` gets everything from `main.ts` through `View3DContext` (fields in
the I_V / I_C slots, levels, alpha, resolution, compute mode, flags, point
sets, colour map + LUT; `invalidate` for asynchronous count readbacks) so it
owns no controls. It implements `MemoryUser` (`memory()`, `trim()`) for the
memory cap. Per frame:

* **compute = gpu** — `sampleResidentSync` the I_V field on the cube grid
  (the adaptive resolution along the longest side, 16 … 256, see
  [resolution.md](resolution.md); byte-accounted LRU caches), build / reuse
  the fused kernel per (grid identity, colour field), one resident mesh per
  level (re-dispatched when the level changes). Every dispatch reads its
  triangle count back: the mesh is sized from the field's measured
  complexity, an overflow (count > capacity) reallocates and re-dispatches.
  The system panel's `iso res` row shows the grid and the triangles drawn.
* **compute = cpu** — `sampleOn` the grid, `marchingTetrahedra` per level with
  the exact gradient (symbolic) and `colourAt = I_C.value(p)`, `uploadMesh`.

Interaction on the overlay canvas: drag orbits — horizontal motion turns the
camera about the world vertical (a turntable; the sense is reversed while the
camera is upside down so the scene always follows the pointer), vertical
motion about the camera's own right axis with no limit, so the camera rolls
over a pole and comes back upside down (`View3D.orbit`, 0.008 rad / px) —,
shift-drag / right-drag pans the target in the view plane, wheel zooms,
`fit` / R reframes the box. The `view` row's presets `xy` / `yz` / `xz` look
at that plane face-on (down the third axis: from +z, +x and −y so the
remaining axes read x right / y up, y right / z up, x right / z up) and
`xyz` from the (1, −1, 1) diagonal, each refitting the box
(`View3D.look(dir)` = `quatLook`, z up on screen, y up when looking along
z). A preset counts as a customised camera. A
customised camera is saved per space; a fitted one is re-fitted when the box
changes or the window resizes.

Like the 2D arm, the camera frames the *free* region of the viewport right of
the left column (`viewRegion()` in main.ts, handed over as
`View3DContext.region`), not the whole canvas: `GpuScene3D.region` (fractions
of the canvas) makes `cameraMatrices` build the perspective for the region's
aspect and shift / scale it in clip space so the camera axis passes through
the region's centre — an off-centre frustum, the panels' strip simply shows
periphery. `fit` uses the smaller of the vertical fov and the region's
horizontal one so the bounding sphere fits a tall region too; `pan` scales
pointer motion by the region height. The overlay projects through the same
`viewProj`, so points and labels stay aligned.

## Streamlines

The `streamlines` panel and the S∇ / S_C matrix columns are shared with the 2D
arm, with the same meaning: `dir` (ascending / descending), `mode` (bi-strat /
strat / JL / cover), `lines`, `length`, `tail`, `split`, particles, colour by
S_C. Lines are integrated through the S∇ field sampled on the volume grid
(step ½ cell), as in 2D. `compute = gpu`: a resident 3-channel grid and
`fusedStreamlines3` (`gpu/src/fused3d.ts` — RK4 both ways within the seeds'
budgets, trilinear, `Seg3` records with colour at the ends); JL / cover plans
are sequential and come from core's planner through a sampled copy, then the
kernel re-integrates the planned seeds within their budgets. `compute = cpu`:
core integration, uploaded. Core's `evenlySpacedStreamlines` and `PointHash`
are dimension-generic now: in 3D the candidates sit at ±d_sep along two
perpendiculars of the tangent (the 2D path is unchanged). Lines are opaque and
depth-tested: they hide behind opaque shells and show dimmed through
translucent ones, which reads well.

## Vector field glyphs

The `vector field` panel and the V∇ / V_C columns are shared too
([glyphs.md](glyphs.md)): arrows on a **face-centred cubic** lattice (the
densest 3D packing; four interleaved cubic grids) inside the cropped box ∩ the
field's box, anchored at the field's box corner. The spacing is the control's
pixels at the camera's target depth, doubled (glyphs at every depth share the
screen), so zooming in refines the lattice and a small crop is a close-up.
`compute = gpu`: `fusedGlyphs` (one kernel per V∇ / V_C, the lattice a
dispatch parameter) into a resident `Seg3` set re-dispatched when the lattice
changes; `compute = cpu`: core samples the cosets and builds the arrows,
uploaded per lattice. The normalizing maximum (the longest vector on the
lattice) is read back for the panel's `longest` readout only. Opaque,
depth-tested like the streamlines; the 3D line pipeline has no alpha. The
`triangle` style is drawn as ray-cast cones (impostors with true depth and a
subtle headlight, `CONES3` in `render3d.ts`; see glyphs.md).

## What the prototype taught, and where it went

* Face outlines are the single most useful reading aid for isosurfaces →
  ported (exact, and consistent with the mesh boundary).
* No 3D colorfield in the prototype: colouring the VOLUME cascades badly
  (occlusion, legend, slices) → colour lives on the surfaces (I_C), and the
  colorfield is shown on up to three axis-aligned PLANES through the volume
  instead (the `colorfield` panel's x / y / z sliders, off by default).
* Weighted-blended OIT beats sorting/peeling for many translucent shells →
  ported; opaque shells go through the depth pass.
* Analytic gradients wherever available (the prototype used stored backprop
  gradients for normals) → here they are exact and also move the vertices.
* Two-sided shading with the far side darker, a headlight → ported.
* Smoothing the metric (blur) is what makes sampled loss landscapes readable
  → ported; Taubin surface smoothing ported on the CPU.
* Temporal supersampling while idle (jittered projection, averaged) → not
  ported yet.

## Planned streamlines and net fields

JL / coverage planning is sequential CPU work and needs the S∇ field as a
dense grid. The 3D arm used to build that grid with `sampleOn` — the CPU
reference evaluator, which for a net-backed gradient at 64³ points is tens of
seconds on the main thread (Safari appeared frozen). It now reads back the
resident vector grid the fused kernel already samples on the GPU
(`readGrid`, asynchronous; the layer keeps showing the previous set until it
lands), as the 2D arm always did through `sampler.request`. The planning
itself is ~80 ms of JS.

## Translucent lines

A 3D line layer with `alpha < 1` (the streamlines' `opacity` slider) is drawn
in the weighted-blended OIT pass together with the translucent meshes
(`linesTrans` pipeline: the same `accum` / `reveal` targets and blend state,
depth-tested against the opaque image, no depth write), so lines and shells
composite without sorting. In that mode a particle tail keeps its width and
fades in OPACITY from `alpha` at the head to 0; opaque lines keep the old
look — width tapering to nothing as the tail fades to black.

## Fling

An orbit drag released while the pointer is still moving keeps the camera
turning (`View3D.flingTrack / flingRelease / flingTick`): the drag's motion
is tracked with timestamps, and on release the mean velocity of the last
80 ms is taken — a click, or a drag whose pointer came to rest before the
release, has no recent motion (or too little: the minimum is 40 px/s) and
does nothing. The frame loop advances the spin every frame (render-only
frames: the resolution controller judges them as draws); any pointerdown
cancels it. Space does not pause a fling — it is not an animation of the
data. No friction: the spin is constant until the next click. The spin runs
at an EIGHTH of the release velocity (`FLING_GAIN`: a slow fling is hard on
a trackpad and a full-rate flick spins too fast to look at) and is AXIS
QUANTIZED: a release within 30° of horizontal or vertical becomes a pure
yaw (the camera circles the vertical) or a pure pitch spin, the small
other component dropped, so the surface turns about one axis instead of
drifting obliquely; an oblique release keeps its direction. A pitch spin
tumbles through the poles forever (the quaternion camera has no clamp).
